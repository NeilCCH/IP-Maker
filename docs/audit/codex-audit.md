# 品牌工作室獨立審計報告

## 給非工程師的摘要

目前的登入、申請審核與管理者權限有基本防護，既有 51 項測試也全部通過；但測試通過不代表可以放心接受別人提供的進度檔。本次找到 **9 項問題（高 2、中 5、低 2）**，其中兩項可讓原本應該只是資料的內容變成程式。最需要先處理的三件事：**① 修補舊版進度匯入的照片檢查，避免打開照片題就執行惡意內容；② 修補 Google 表單程式產生器，避免品牌名稱夾帶程式；③ 補上重新連線時的權限檢查，讓已停用的人回到線上後確實被帶回登入頁。** 建議先完成這三項及對應測試，再擴大團隊使用。本次沒有對正式網站進行測試，也沒有修改應用程式。

## 已確認的發現

### F01｜高：舊版照片欄位可在匯入後執行 JavaScript

- **位置**：`app/js/model.js:172`（來源檢查）、`app/js/model.js:210`（遷移分流）、`app/js/views/profile.js:90`（APP 插入點）、`app/js/website.js:136`（匯出 HTML 插入點）。
- **問題**：v2 的 `sanitize()` 對照片採完整格式與長度檢查，但 `fromLegacyV1()` 只檢查開頭，並直接回傳資料，沒有通過相同的清理。照片再未經屬性跳脫放入 `src="…"`。引號可以結束 `src` 並新增事件處理器。
- **本機重現**：在 APP 的「進階工具 → 匯入進度」匯入下列舊格式，接受取代進度，再於同一頁面生命週期進入照片題：

  ```json
  {"answers":{"photo":["醒目呈現"]},"entries":[],"photo":"data:image/png;base64,AA\" onerror=\"window.__auditPhoto=1"}
  ```

  Chromium 中 `window.__auditPhoto` 變為 `1`。此標記不讀取或傳送資料。也確認相同遷移資料產出的個人網頁包含未跳脫的 `onerror` 屬性；預覽 iframe 的空沙箱不能保護 APP 本身的照片題，或下載後獨立部署的 HTML。
- **影響／前提**：需要使用者匯入攻擊者提供的進度檔，並進入相關畫面；不是單憑未登入請求即可利用。成功後可讀取同來源品牌資料，並以目前登入身分呼叫同來源 API；若受害者是管理者，影響可能包含審核功能。HttpOnly 可阻止直接讀 Cookie，不能阻止同來源程式代發請求。
- **修正方向**：所有遷移格式最後都走同一套正規化與嚴格照片驗證；HTML 屬性仍須跳脫，最好透過 DOM 屬性設定。補上舊格式照片注入、超長圖片與匯出 HTML 的測試。不能只依靠重新整理後 v2 清理掉資料。
- **確信度**：高；APP 執行已本機重現。

### F02｜高：品牌名稱可跳出 Google 表單程式的註解

- **位置**：`app/js/entries.js:87`–`94`，尤其第 88 行；呼叫端 `app/js/views/results.js:302`、`app/js/export.js:115`。
- **問題**：程式中的字串值有用 `JSON.stringify()`，但檔頭區塊註解直接放入品牌名稱。名稱中的 `*/` 可結束註解，後續內容成為頂層程式。
- **本機重現**：將品牌名稱設為 `*/globalThis.__auditGS=1;/*`（未超過 30 字限制），呼叫 `formScript(state, derive(state))`，在隔離的 Node VM 執行產出字串。無須呼叫 `createBrandForm()`，無害標記即成為 `1`。沒有在 Google 帳號執行。
- **影響／前提**：攻擊者可透過他人匯入的品牌檔提供名稱；受害者還必須依 APP 引導複製、授權並執行產出的 Apps Script。程式會在受害者授權的 Google 專案環境執行，實際可存取範圍取決於該專案權限；本次未驗證雲端資料存取。這是程式碼注入，不只是外部 AI 的提示詞風險。
- **修正方向**：檔頭註解不插入自由文字，或採安全的單行註解編碼；維持程式字串的 JSON 編碼。新增含 `*/`、換行與特殊字元的產出程式測試，確保頂層不會新增可執行敘述。
- **確信度**：高；產出字串的程式注入已本機重現。

### F03｜中：離線開啟後，恢復連線不會重新檢查權限

- **位置**：`app/js/main.js:134`–`140`、`app/js/auth.js:22`–`38`、`app/sw.js:54`–`60`。
- **問題**：`checkAccess()` 只在入口初始化呼叫；離線失敗後允許繼續使用，但沒有 `online` 或回到前景時的重新檢查。快取優先策略使頁面也不必重新經過伺服器門禁。
- **本機重現**：先以模擬核准帳號快取 APP，離線重新載入，再把本機伺服器狀態改為未登入並恢復網路。觸發 `online` 後，`/api/me` 的伺服器呼叫數仍為 `3 → 3`，APP 仍可編輯，未清快取或導回申請頁。
- **影響／界線**：Worker 的 session 撤銷仍有效，管理 API 仍有權限檢查；**不是伺服器權限繞過**。問題是已經上線的快取 APP 未按專案承諾重查權限。既知的「完全離線仍可用」不列為漏洞。
- **修正方向**：在恢復網路、回到前景等時機重查權限並防止重複並行；拿到明確未授權結果時清除 APP 快取、導回門禁。保留原先允許的真正離線編輯行為。
- **確信度**：高；本機連線切換重現。

### F04｜中：舊版共用品牌資料遷移會無聲丟失照片與視覺偏好

- **位置**：`app/js/model.js:188`–`202`；舊格式來源 `legacy/demo-v3/app.js:53`。
- **問題**：舊 `brandKit()` 確實匯出 `visual.photo`、`visual.photoPreference`、`visual.style`，但 `fromKitV1()` 沒有搬移這三項。
- **重現**：匯入 `schemaVersion:1` 的品牌檔，設定合法圖片於 `visual.photo`、`visual.photoPreference:["不放照片"]`、`visual.style:["親切自然"]`。`migrate()` 結果分別為 `photo:""`、`answers.photo:[]`、`answers.style:[]`，且匯入顯示成功。
- **影響**：原本照片與外觀設定消失，使用者不知道需要重選；未來重新上傳照片時，也不再保有「不放照片」的選擇。這不是原檔被刪除，而是還原結果不完整。
- **修正方向**：明確對照舊格式欄位並透過共同清理流程遷移；不能保留的欄位應列出提醒。補上從真正舊版匯出檔還原的欄位對照測試。
- **確信度**：高；以舊版來源與本機遷移結果交叉確認。

### F05｜中：LINE 雙頁上傳失敗後，只回復預設選單不足以復原原狀

- **位置**：`app/js/line.js:91`–`105`，尤其第 99–100 行的 alias 更新。
- **問題**：每完成一頁就建立／更新固定名稱 `brand-page-1`、`brand-page-2` 的 alias，兩頁全部成功前已可能改到原選單使用中的 alias。備份卻只有原本的預設選單 ID；沒有保存 alias 原對應，也沒有失敗回復流程。
- **本機重現**：以不連網的 `curl` 替身模擬既有 alias：第一頁圖片上傳成功、alias 建立回應衝突、更新成功；第二頁圖片上傳回傳失敗。腳本以狀態碼 22 中止；紀錄顯示 `brand-page-1` 已指向 `new-1`，但第二頁未完成，沒有回復請求。JSON 引號與 `bash -n` 檢查正常。
- **影響／前提**：需要更新曾用相同 alias 的帳號。舊選單的切頁可能進到新舊混用狀態；把 default ID 設回去，也無法把已改動的 alias 設回。供應商有 alias 快取，手機上何時反映仍待確認。
- **修正方向**：先驗證全部設定並建立／上傳所有頁面，再切換；使用每次發佈獨立的 alias 名稱，或完整備份 alias、default 並提供回復步驟。失敗時列出已建立資源與處理方式。增加全成功、第二頁失敗、重跑與回復的腳本模擬測試。
- **確信度**：高；本機腳本控制流程重現，未操作真實 LINE 帳號。

### F06｜中：個人網頁把自選特質寫成未經證實的客戶評價

- **位置**：`app/js/copy.js:102`；資料來源 `app/js/brand.js:226`、`app/js/data/questions.js:38`–`45`。
- **問題**：問卷讓本人選「最像自己／希望客戶記住」的詞，網頁卻自動產生「客戶常說我……」。問卷並未取得實際客戶評價。
- **重現**：新資料只設定 `answers.keywords:["沉穩"]`，呼叫個人網頁 `about` 文案產生器，即得到「客戶常說我沉穩。」。不需要填任何經歷或客戶回饋。
- **影響**：新進或尚未有客戶回饋的同仁可能直接發布虛構第三方背書，違反專案不虛構原則。後面的經歷待填欄位不能消除此句既有宣稱。
- **修正方向**：改為本人定位或期望的描述；若要客戶評價，另設明確的真實來源欄位，未提供時不生成。
- **確信度**：高；本機文案結果已確認。

### F07｜中：鍵盤使用者無法操作匯入與照片上傳入口

- **位置**：`app/js/views/advanced.js:25`、`app/js/views/profile.js:92`；`app/css/app.css:27`。
- **問題**：可點擊的外觀是沒有 `tabindex` 的 `<label class="btn">`，內部 file input 又有 `hidden`，CSS 將其設為 `display:none`。兩者都不會進入一般 Tab 焦點順序，程式也沒有鍵盤替代操作。
- **重現**：進階工具用 Tab 導覽，會跳過「匯入進度」。本機讀取屬性為 input `hidden:true`、`display:"none"`、label `tabIndex:-1`。照片控制使用相同結構。
- **影響**：只用鍵盤的人無法從介面還原資料或選照片；滑鼠點擊可用不代表鍵盤可用。
- **修正方向**：保留可聚焦、有明確標示的原生 file input，或用真正的 button 在使用者操作事件中觸發選檔。補上只用 Tab／Enter／Space 的完整還原及上傳測試，並驗證輔助科技名稱。
- **確信度**：高；DOM／CSS 與本機焦點屬性已確認。

### F08｜低：匯入的小數題號通過檢查，會使問卷畫面中斷

- **位置**：`app/js/model.js:103`、`app/js/views/profile.js:166`–`169`。
- **問題**：題號只夾在上下限，沒有要求整數。`0.5` 可通過 `sanitize()`，但 `QUESTIONS[0.5]` 是 `undefined`。
- **重現**：以 `fresh()` 產生合法 v2 檔，只將 `meta.qIndex` 改成 `0.5`，從介面匯入，再開第一步。本機出現 `Cannot read properties of undefined (reading 'type')`。重新整理也不會修正該題號。
- **影響**：不需要惡意程式就可讓目前進度無法正常開問卷；可經進階工具還原正常備份，並非不可回復的資料銷毀。
- **修正方向**：題號採有限整數與範圍檢查；渲染端提供安全回退。補上小數、非數值、負數與超出範圍的匯入測試。
- **確信度**：高；透過實際匯入與畫面切換重現。

### F09｜低：自訂主色的對比檢查漏掉一般文字所需的 4.5:1

- **位置**：`app/js/brand.js:120`、`app/js/website.js:107`；加深目標見 `app/js/brand.js:149`。
- **問題**：只有主色對白底小於 3:1 才顯示衝突，但產出網頁的按鈕是 17px、粗體白字，不符合可只要求 3:1 的大字條件。程式自己的自動加深目標其實是 4.5:1。
- **重現**：選自訂主色 `#888888`；`contrast('#888888','#ffffff')` 為約 `3.54`，`detectConflicts()` 卻不回報 `custom-contrast`。輸出按鈕仍是該背景加白字。
- **影響**：使用者沒收到提醒，就可能下載對比不足的聯絡按鈕。預設色票不因此被認定全部有問題。
- **修正方向**：按文字實際大小採合適門檻，至少一般字需 4.5:1；同時檢查主色與實際背景、按鈕前景，而非僅抽象色票。加入接近門檻的色碼測試。
- **確信度**：高；色彩數值及輸出 CSS 已核對。
